# Super Pro Coding Guard

用于本仓库所有“需要真正写代码”的任务。目标是先识别改动边界、读取最小必要上下文，再用最小充分改动完成前端、后端、shared 或跨层变更，并留下可验证闭环。

## 动作流 1：识别改动面

1. 先读取 `references/project-map.md`。
2. 先判断改动属于以下哪一类：
   - 前端应用
   - 后端服务
   - shared 包
   - 跨层契约
   - 配置、脚本或测试
3. 先读取 `references/change-shape.md`，明确本次是新增、修改还是删除。
4. 如果触达前端，再读取 `references/frontend-delivery-flow.md`。
5. 如果触达后端，再读取 `references/backend-delivery-flow.md`。
6. 如果触达 shared 包、权限码、常量、接口类型或同时影响前后端，视为跨层改动，前后端 reference 都要读。

## 动作流 2：装载必要上下文

1. 先读目标目录的现有实现，不要脱离现状重写。
2. 前端任务至少确认：
   - `design.md`
   - 目标应用主题来源，如 `src/theme.css`
   - 现有页面、组件、路由、API 目录
3. 后端任务至少确认：
   - 目标服务的入口、router、controller、service、repository、dto、entity
   - 现有运行时、日志、异常、鉴权接法
4. shared 任务至少确认：
   - 当前 export 入口
   - 现有消费者
   - 是否会影响前后端编译或契约
5. 任何跨层改动都要同步确认提供方和消费方，而不是只改单边。

## 动作流 3：约束实现方式

1. 先搜索现有能力，再决定是否新增文件、模块或抽象。
2. 先复用 shared 包和既有模式，再补共享能力，不要在业务目录复制一套。
3. 先补边界，再补实现：
   - 前端先定页面、组件、API、权限边界
   - 后端先定路由、DTO、权限、分层边界
   - shared 先定导出面和消费者影响
4. 删除功能时，要同步移除直接相关的路由、菜单、导出、测试、样式和引用，避免留下悬挂代码。
5. 除非用户明确说明不需要权限校验，否则只要涉及页面准入、菜单、按钮、用户信息显示、受保护 API、新增或修改接口，就默认接权限边界。
6. 每一处改动都应能回溯到用户请求，不顺手扩写无关能力。

## 动作流 4：落地编码

1. 前端改动时，按 `references/frontend-delivery-flow.md` 执行。
2. 后端改动时，按 `references/backend-delivery-flow.md` 执行。
3. 如需快速起手，先读取 `references/template-index.md`，再从 `assets/templates/*` 复制最接近的模板。
4. 模板只用于加速，不要整块照搬；落地前要把占位符、权限码、接口路径、DTO 字段和错误消息替换成真实业务值。
5. shared 或跨层改动时：
   - 先更新 shared 导出、类型、常量或基础能力
   - 再更新直接消费者
   - 再核对是否需要补权限码、响应类型或错误处理
6. 修改现有能力时，优先保持原有接口稳定；如果必须改契约，要同步修改消费者和验证。
7. 删除现有能力时，优先做“完整摘线”，不要只删主文件而保留引用入口。

## 动作流 5：验证与收尾

1. 按 `references/verification-matrix.md` 选择最小但有效的验证命令。
2. shared 改动至少验证 shared 本身；跨层改动额外验证直接消费者。
3. 涉及权限时，至少验证：
   - 未登录 `401`
   - 已登录无权限 `403`
   - 有权限成功
4. 涉及前端时，额外检查桌面端、平板、移动端，以及受影响浮层、菜单、表单或路由。
5. 最终说明必须交代：
   - 实际读取了哪些上下文
   - 复用了哪些 shared 能力
   - 新增、修改、删除了哪些关键边界
   - 跑了哪些验证
   - 还有哪些未验证项和风险

## 阻断条件

以下情况要先停下来说明问题：

- 无法确认目标目录、现有实现或消费者
- 前端缺少主题来源且无法确认回退方案
- 后端无法确认鉴权链路、权限码来源或运行时接法
- shared 导出变更会影响多端，但无法确认受影响面
- 用户要求与现有共享边界、权限边界或契约直接冲突

## Admin Single Page Template

当任务是在 `admin-front` 中新增、修改或重构“单页面后台布局”时，额外执行下面动作流：

1. 先读取 `references/single-page-layout.md`
2. 优先检查 `admin-front/src/pages/admin/module-page-shared.tsx` 的现有布局常量是否可复用
3. 如需快速起页，优先复制 `assets/templates/frontend/admin-single-page.template.tsx`
4. 根页面 `section` 默认占满内容区，不加额外外边距，不再套窄内容容器
5. 搜索区使用轻量顶部工具栏容器，主体区使用填充型内容容器
6. 搜索区、表格壳子、状态提示区默认不用 `Card` 作为纯布局容器
7. 只有信息分组本身成立时，才允许保留或新增 `Card`
8. 页面完成后，按 `references/page-detail-checklist.md` 和 `references/verification-matrix.md` 收口
