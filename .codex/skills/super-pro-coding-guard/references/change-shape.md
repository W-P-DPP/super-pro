# Change Shape

在开始编码前，先用本文件判断这次是新增、修改还是删除，并按对应动作流约束范围。

## 新增

1. 先找目标领域最接近的现有实现。
2. 先确认应该落在业务目录还是 shared 包。
3. 先补边界，再补实现：
   - 新页面先定路由、入口、权限和 API 边界
   - 新接口先定路由、DTO、权限和响应契约
   - 新 shared 能力先定导出面和消费者
4. 再补最相关测试或验证命令。
5. 最后确认新增能力是否需要菜单、导出、常量、权限码或文案同步。

## 修改

1. 先识别当前契约是否允许保持兼容。
2. 先做最小充分补丁，不顺手重构整片区域。
3. 如果修改 shared 类型、常量或行为，先列出直接消费者。
4. 如果修改接口、页面入口或权限判断，同步核对调用方和依赖方。
5. 如果行为改变，补最相关验证，不只看编译通过。

## 删除

1. 先确认删除的是功能、入口、导出，还是仅删除一层实现细节。
2. 先搜索引用，再摘线，再删主体代码。
3. 同步移除与该能力直接绑定的：
   - 前端路由、菜单、按钮入口、API 模块、页面测试、样式引用
   - 后端路由注册、控制器入口、DTO、权限码种子、测试
   - shared 导出、消费者引用、示例和构建依赖
4. 删除后再次搜索，确保没有悬挂 import、export、类型或命令入口。
5. 删除不等于大扫除；只移除与这次请求直接相关的残留。

## 跨层同步

以下内容一旦变更，就要同步核对上下游：

- `@super-pro/shared-types`
- `@super-pro/shared-constants`
- `@super-pro/shared-web`
- `@super-pro/shared-server`
- 权限码、响应结构、路由路径、认证要求

## 默认避免

- 不在单次任务里顺手引入新架构层
- 不在业务目录复制 shared 能力
- 不只删主文件而保留菜单、导出、测试或调用入口
