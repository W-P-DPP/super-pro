# 全栈开发自动提交工作流

这个 skill 是一个编排器。它不替代已有的前端、后端和提交规范 skill，而是按固定顺序串联它们，完成一次从实现到验证再到提交的完整交付。

## 触发后的固定顺序

1. 先检查任务是否同时涉及前端、后端、共享契约或联调交付。
2. 读取当前代码和工作区状态，确认变更范围、目标应用、目标服务以及是否存在无关脏改动。
3. 前端阶段显式遵循 `$frontend-design-guard`。
4. 后端阶段显式遵循 `$backend-dev-guard`。
5. 如果前后端通过共享类型或接口契约耦合，回到前端阶段完成接线和联调收口。
6. 运行最小且有意义的验证。
7. 提交阶段显式遵循 `$git-commit-convention`，然后执行 `git add` 和 `git commit`。

## 第零步：先做边界判断

先确认以下问题：

- 目标前端包是哪个，例如 `agent-front`、`reimburse-front`、`summary-front`、`frontend-template`、`login-template`。
- 目标后端服务是哪个，例如 `agent-server`、`reimburse-server`、`general-server`。
- 是否涉及 `packages/shared-types`、`packages/shared-web`、`packages/shared-server`。
- 当前工作区是否已有无关修改。

边界规则：

- 如果任务其实只涉及前端或只涉及后端，不要强行制造另一侧改动。
- 如果当前工作区存在无关脏改动，不要把它们顺手提交进去。
- 如果目标文件里混有无法区分归属的用户改动，停止自动提交，只完成实现和验证，并明确说明原因。

## 第一步：读取工作区和现有实现

实现前先做这些检查：

- 查看 `git status --short`。
- 查看目标前端包和目标后端服务的现有目录结构。
- 查看相关 API、共享类型、共享工具和已有页面或模块模式。
- 不要在不了解现有实现的情况下直接新建一套并行结构。

如果任务跨前后端：

- 先识别依赖链，判断是前端先定义交互需求、后端先补能力，还是先补共享契约。
- 以最小阻塞路径推进，不要机械地把“前端优先”理解成必须先写完前端代码。

## 第二步：执行前端阶段

前端阶段必须显式使用 `$frontend-design-guard` 的约束。

执行要求：

- 先读取仓库根目录 `design.md`。
- 再读取目标前端项目自己的 `theme.css`；如果不存在，再回退到前端 skill 自带参考。
- 检查目标应用的 API 模块、鉴权跳转、共享类型和响应式模式。
- 页面和视觉组件不要直接发请求，API 收敛在 `src/api/modules/*`。
- 默认使用简体中文前端文案，除非用户明确要求其他语言。
- 默认同时适配桌面端和移动端。

如果前端依赖缺失的后端能力：

- 先把需要的接口、字段、错误态、鉴权要求和响应结构整理清楚。
- 不要在前端本地发明一个与后端不一致的数据结构。

## 第三步：执行后端阶段

后端阶段必须显式使用 `$backend-dev-guard` 的约束。

执行要求：

- 先检查接口归属，判断应该进入 `general-server` 还是业务专属服务。
- 优先复用 `packages/shared-server`，不要在服务里复制基础设施能力。
- 保持 `router -> controller -> service -> repository -> entity` 的清晰边界。
- DTO、响应结构、鉴权和异常处理要与仓库现有约定一致。
- 新接口默认考虑 JWT 保护；匿名接口必须显式声明。
- 邮件模板、接口消息和测试文案默认使用简体中文。

如果后端变更会影响前端契约：

- 明确同步更新共享类型、API 模块或前端映射逻辑。
- 不要只改服务端而遗漏前端接线。

## 第四步：联调与共享契约收口

当前后端都改动过时，必须做一次收口。

收口要求：

- 对照前端调用和后端响应，检查字段名、包络结构、鉴权行为和错误态是否一致。
- 如果任务涉及共享类型，把变更收敛到 `packages/shared-types` 或既有共享契约位置。
- 如果任务涉及浏览器公共能力或服务端公共能力，分别优先落到 `packages/shared-web` 或 `packages/shared-server`。
- 如果前端为了等待后端而写过临时假数据、绕过逻辑或占位实现，提交前必须清理。

## 第五步：验证

提交前至少做最小但真实的验证，不要跳过。

验证原则：

- 只跑和本次改动直接相关的命令，但要足够证明修改有效。
- 优先跑目标应用或目标服务的定向验证，再决定是否补更大范围验证。
- 最终说明里明确写出实际执行过哪些命令，哪些没跑。

常见验证范围见 [references/workflow-checklist.md](references/workflow-checklist.md)。

## 第六步：自动 Git 提交

提交阶段必须显式使用 `$git-commit-convention` 的约束。

执行顺序：

1. 先用 `git status --short` 重新确认工作区。
2. 只暂存本次任务拥有的文件，不要把无关文件一起加入提交。
3. 用 `git diff --staged --stat` 和 `git diff --staged` 检查最终提交内容。
4. 根据 staged diff 生成 Conventional Commit 信息。
5. 使用非交互方式执行 `git commit`。

提交规则：

- 如果一个变更集包含多个无关目的，拆成多个提交，不要硬塞进一个 commit。
- 如果存在无关脏改动但可以隔离，使用显式路径 `git add <path>` 只暂存目标文件。
- 如果无法安全隔离目标改动，不要自动提交，改为向用户说明阻塞点。
- 不要使用交互式 git 流程。
- 不要使用破坏性 git 命令。

## 输出要求

完成任务后的说明至少包含：

- 本次前端改了什么。
- 本次后端改了什么。
- 哪些共享契约或共享包发生了变化。
- 实际运行了哪些验证命令。
- 最终使用的 commit message 是什么。
- 如果没有自动提交，明确说明原因。

## 示例请求

以下请求适合触发这个 skill：

- “帮我做一个前端页面加后端接口，最后直接提交 git。”
- “把报销页面和报销服务一起改完，跑完验证后自动提交。”
- “完成这个跨前后端需求，最后帮我按仓库规范提交。”
